## The principles we settled
1. **Research only.** What we record is for study on our side. It never gives users music, orders their feed, ranks search, or chooses what plays.
   (This extends the 10 Oct rule: the site connects people, it never recommends tracks.)
2. **Opt-in, one switch, off by default.** `user_prefs.keep_listening` in `activity.db`. Today only `lnv_admin` is on.
3. **Ids and slug labels only.** No post or reply text, no search terms, no IP, no screen positions. The server drops anything that is not a tidy slug.
4. **YouTube data never kept past 30 days.** We refresh it. We do not copy it to another store, and we did not build a patch day.
5. **Measure, then fix, and say what could not be measured.**

## What was built, by theme

### Labels and search
- **Add a label from Bandcamp** (`/api/custom-labels`, Labels drawer "＋ Add a label"). Paste a Bandcamp page; it shows what it read plus similar Discogs
  labels and asks "Is this the label you meant?" before saving. Releases live in `discogs_catalogue` under a negative entity id. Only `*.bandcamp.com` works.
- `GET /api/users/search?q=`.

### Links and the YouTube rules
- **30-day refresh** (`services/youtubeRefresh.js`): hourly; refreshes stored YouTube data older than 25 days with `videos.list` (1 unit per 50);
  clears gone / private / embedding-off ones; hard-stops anything past 30 days even if the API is down. Google's wording: III.E.4.d.
- **Wrong-link flagging** (`badLinks.js`, `badLinkStore.js`): report, replace, withdraw. Flagged on 2 reports, an admin report, or a replacement that
  clearly fits. A trigger on `release_track_links` refuses flagged links; the YouTube search skips them.

### Performance and memory
- Launch: **scroll locked until everything has loaded** (`lib/launch.js`: the reveal animation, the fonts, the feed's first page and every card on the page; opens once, for good; a timer opens it after 8 s whatever happens so nothing can stick), counter removed. **Smoother reveal:** the cover used to be resized from JavaScript every frame (layout + a re-rasterised 3-gradient mask on the main thread, which React was also busy on); it is now one panel moved with `transform` via the Web Animations API (compositor, off the main thread), clipped at the rail, with two small static corner pieces; 2.2 s (was 1.8 s), ease-in-out (was an abrupt ease-out); no animation for reduced-motion users. Check it by eye in a visible browser: the pane here cannot play animations. Spotlight cards lighter (30 rows, 24-sleeve strip). On-demand loading of the post window
  and admin drawer. Eight dead files removed. **Per-post lookups indexed. Prepared-statement cache** (mean request 8.9 to 5.0 ms).
  Bandcamp covers load at display size. Cache cap on the nightly job. **Memory sampler** with a trend in Admin Status.
- **Smooth start (committed, not deployed):** the lag at the start was the first request asking for 60 posts and React building all 77 cards in one
  339 ms task as the animation began. Now: first page 20, cards mounted 6 then 4 per task. Zero long tasks during load.

| | Before | After |
|---|---|---|
| DOM elements on the feed | 22,430 | 14,705 |
| Layout after a scroll step | 12.2 ms | 6.8 ms |
| Full style recalculation | 110 ms | 67 ms |
| Main script | 849 KB | 735 KB |
| Feed page lookups at 5,000 posts | 134 ms | 8 ms |
| Mean request (dev data) | 8.9 ms | 5.0 ms |
| Bandcamp cover decode | 16.5 MB | 1.4 MB |
| Startup main-thread blocking | 529 ms (339 ms worst) | 0 |

**Server memory:** 1.15 GB resident is 900 MB of mapped database (by design) + a 128 MB SQLite cache; the program itself is about 176 MB, and the
service's cgroup shows 219 MB. No leak found in 8,000 mixed requests. My earlier claim that one cache explained the 1.2 GB was wrong (corrected in the memory report).

## How to undo things
| Thing | Switch |
|---|---|
| Statement cache | `LNV_STMT_CACHE=0` in `/opt/lnv/backend/.env`, restart |
| Memory sampler | `MEMORY_WATCH=0` |
| YouTube refresh | `YT_REFRESH=0` (and `YT_REFRESH_UNITS_PER_DAY` to cap units) |
| Nightly spare-quota job | `SPARE_QUOTA=0` |
| Recording for an account | `PUT /api/activity/me/settings {keep_listening:false, clear:true}`, or `DELETE /api/activity/me` to remove everything held about them |
| Any commit | `git revert <hash>`; none rewrote history |

## Deploy routine and gotchas (learned today)
- On the server as root: `cd /opt/lnv && git pull`, then `chown -R lnv:lnv .git backend/routes backend/services backend/db frontend/src`,
  then `cd frontend && npm run build` (as root), then `systemctl restart lnv`. Verify with `curl https://waxopathy.com/api/...`.
- Reading the server's `.env` was blocked by the safety classifier; reading `/proc`, `journalctl` and `sqlite3` counts was fine. Do not work around a denial.
- **Line endings:** Git rewrites working copies to CRLF, so multi-line text matching fails on files you just committed. Use CRLF-aware edits.
- **Never `git stash` here:** it sweeps up your uncommitted `moduleKit.js`.
- **The built-in browser pane is hidden in this setup:** no animation frames, no `IntersectionObserver`, `content-visibility` never toggles, timers throttle.
  Anything about real scrolling, fps or lazy-loading triggers needs a visible browser.
- A fresh empty database cannot boot the full server (an old migration ordering quirk: `release_track_links.paid`). Tests used throwaway databases with
  the needed columns pre-created.
