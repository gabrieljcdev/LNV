### 8. Main feed · walls · following · playlists (built 3 Oct, commit 8b62949)

gabriel's model after the show-and-tell (it changed twice during the day —
this is the final one): **a main feed, a personal feed (your wall), and
playlists.** Collaboration happens in playlists, not walls or shared feeds.

- **Home view:** visitors land on the main feed; **signed in, you land on
  "my feed"** (`GET /posts?feed=home`): your posts + everyone you follow,
  numbered by place in that feed, followed posts tagged "following"
  (`followedFrom`). The strip's first tab says "my feed" once signed in;
  the main feed is in the switcher. Signing in/out resets to the home view.
- **Walls** (`GET /posts?wall=<username>`, public): the posts a user made —
  a post goes on its poster's wall (`posts.wall_user_id`) and the main feed.
  Your feed only fills by posting a link "the traditional way" (gabriel: it
  should nudge people to post). Every username on a card opens their wall.
  Link: `/?wall=<name>`.
- **Following** = following another user (`follows`; `routes/walls.js`:
  follow / unfollow / `me/following`). "+ follow" sits beside the feed
  switcher on someone's wall; the people you follow are listed in the
  switcher and the Walls drawer to open their walls.
- **Per-feed numbers:** on a wall or a playlist-as-feed the big number is the
  post's place in that feed (`feedNumber`), with "main #N" small in the
  byline (click → main feed, jumps to it; Feed.jsx `lnv:jump-main`).
- **Playlists** (`routes/playlists.js`; tables `playlists` (+kind,
  share_token, invite_token), `playlist_tracks`, `playlist_members`):
  - made of tracks; **♡ on a track** → your "Hearted tracks" playlist
    (kind 'hearted', made on first heart); **+** next to a track / "+ list"
    on a card (tick tracks) → any playlist you own or were invited to.
  - ♡ and + are on card tracklists (single + album cards), live sets (♡ in
    the byline), spotlight track rows (once the track has a link) and
    playlist rows.
  - **share link** `/?playlist=<token>`: anyone, signed out too, can listen
    — read-only; **invite link** `/?playlistinvite=<token>`: friends who join
    can add / remove / reorder tracks (owner renames, deletes, renews links,
    removes friends).
  - **view as feed**: the posts the tracks come from, as cards, in playlist
    order (`GET /posts?playlist=<id>` for members, `?playlist_token=` for
    link holders). Tracks not from a post don't appear there.
  - **Uninterrupted queue** (`lib/queue.js`, `components/QueueBar.jsx`, a
    floating player bottom-right that keeps playing while you browse): plays
    a playlist straight through. Track end: YouTube IFrame API (errors →
    skip), SoundCloud Widget API FINISH, Mixcloud widget `ended`, Bandcamp
    timed from its stored length once you press play in it (no autoplay /
    API). Unplayable links are skipped with a note. Shuffle, repeat (all /
    one), prev / next / stop, hide video. The random ▶ on the strip closes
    it (one player at a time). Checked: skips + controls in the browser;
    a natural track end advancing wasn't waited for (YouTube's API hookup is
    proven by the error-skip; SoundCloud's FINISH hookup is untested live).

### 9. Launch readiness — best and worst case (agreed 4 Oct)

gabriel asked "what if the site blew up — a few thousand users overnight?"
and wants it ironed out before going public, ready for both the surge and
things going wrong. The server itself would cope (Node + SQLite on one
£5–20/month box handles a few thousand users; playback streams from
YouTube / SoundCloud / Bandcamp, not us). What breaks first is the outside
services and the unfinished launch jobs. Several items overlap sections 1,
3 and 6 — this is the one checklist to work from. Rough order:

**A. Must be done before anyone outside is invited**
1. **Hosting + deploy.** A real server (VPS or similar), the domain, HTTPS,
   a process manager (pm2 / systemd — never nodemon in production), the
   frontend built and served, CORS and URLs from `.env` (CORS is
   hard-coded to localhost now), `app.set('trust proxy', …)` behind the
   proxy — **without it every visitor looks like one IP and the 500 /
   15 min rate limit locks everyone out at once.**
2. **Email that scales.** SMTP is empty, so confirm / reset links only show
   on the page. Pick a provider (Resend / Brevo / Postmark…) on a paid tier
   — free tiers are ~100–300 emails a day, which a few thousand sign-ups
   would exhaust, leaving new users unable to confirm. Set up SPF / DKIM /
   DMARC on the real domain so mail isn't spammed; real admin email.
3. **The security pass** (section 6): fresh credentials, `npm audit` fixes,
   helmet headers (CSP allowing the player embeds), httpOnly session
   cookie + CSRF, admin 2FA, per-account lockout, generic production
   errors, smaller JSON limit, iframe sandboxing.
4. **Abuse controls.** Sign-up bot check (Turnstile / hCaptcha), rate limits
   on posting, comments, follows and playlist adds (not just auth), a
   report button on posts / comments / walls / playlists, and admin tools
   to hide a post, suspend or ban an account and see reports. Reserved and
   look-alike usernames (impersonation of artists / labels).
5. **Legal (UK).** Privacy policy (incl. the 30-day log, YouTube API
   Services' required wording + link to Google's privacy policy), terms of
   use, data export + delete account (UK GDPR), a contact address, a
   copyright / takedown process (covers and descriptions come from Discogs
   and platforms), **Discogs attribution** ("Data provided by Discogs",
   their API terms), and the Online Safety Act basics for a user-to-user
   site (risk assessment, reporting, acting on reports). No cookie banner
   needed while there's no tracking (session storage is strictly
   necessary) — keep it that way or add one with analytics.
6. **Phone layout** (section 2: at 375px the strip is 530px and the search
   box is off-screen). A viral spike comes mostly from phones via social
   links — this has to work before launch.
7. **Backups.** Automatic daily copies of `vinyl_crate.db` off the server
   (use SQLite's backup API / `.backup`, not a plain file copy of a live
   WAL database), kept ~30 days, and **a restore actually tried once.**
8. **Purge the dev data** (all current users and posts) and set the real
   name — avoid going viral under a name that then changes (domains,
   handles, trademark check first; section 4).

**B. Best case — the surge**
1. **YouTube quota:** apply for the free increase now (it takes weeks). At
   ~5,000 units a day and 100 per track search, only ~50 searches a day for
   tracks without links — gone by mid-morning in a spike. Also show a clear
   "searching paused for today" state (exists) and lean on the crawled
   channel uploads first (exists).
2. **Discogs:** 60 requests / minute. Queue compose lookups politely, cache
   harder, show "looking it up…" rather than failing; the catalogue crawler
   only runs when the site is quiet, so expect catalogues to stall in a
   spike (fine — say so in the admin Status).
3. **Page scraping** (Spotify, SoundCloud, Beatport, Bandcamp, Tidal): one
   server reading thousands of pages gets blocked (Cloudflare 403s).
   Official APIs first (Spotify Web API — section 1), cache every result,
   back off on errors, fall back to the backup fill.
4. **Endpoints that grow with the site:** `GET /posts/browse` sends every
   post to the drawers — page it / group server-side. Check the feed, wall,
   my-feed and playlist queries with ~50k posts and ~5k users (the
   per-post COUNT numbering needs an index or a stored number at that size).
5. **Load test** before launch (k6 / autocannon on a copy): feed, search,
   compose, sign-up — find the first thing to fall over.
6. **Caching + images:** cache headers on the built frontend; covers are
   hotlinked from Discogs / YouTube — check Discogs' image terms and rate
   limits; consider caching thumbnails ourselves.
7. **Switches to slow growth or shed load:** invite-only / waitlist mode,
   a sign-up cap per hour, and admin toggles to pause expensive features
   (YouTube search, crawlers, page scraping, new sign-ups) without a deploy.
8. **Support load:** an FAQ / help section, a support inbox, and clear
   in-app messages for the common failures (email didn't arrive, link
   expired, can't play this track).
9. **Scaling path written down:** what to do if one box isn't enough —
   bigger box first; then Postgres instead of SQLite, a job queue for
   crawlers / lookups, a CDN. Not needed for thousands; plan for tens of
   thousands.

**C. Worst case — things going wrong**
1. **Monitoring:** uptime check with alerts to gabriel's phone, error
   tracking (Sentry or the admin log + email alerts), disk-space and
   memory alerts (the catalogue DB grows — Columbia alone is ~396k rows).
2. **Server down / bad deploy:** a maintenance page, a rollback plan (tag
   each release, back up the DB before every deploy), safe migrations (the
   current "ALTER and ignore errors" list is fine for adding things, risky
   for changing them — test on a copy of production data first).
3. **Data loss / corruption:** the backups above + a written restore
   procedure; WAL checkpoints; never edit the live DB by hand.
4. **A leaked key or password:** know how to rotate every secret fast
   (Discogs, YouTube, Spotify, SMTP, admin), and "sign out everywhere"
   for all users if sessions are suspect.
5. **Account takeover / XSS / spam wave:** the security pass, the bot
   check, rate limits, and the admin ban / hide tools from A4 — plus a
   one-switch "read-only mode" to freeze posting while cleaning up.
6. **Takedown or legal complaint:** the copyright process from A5, a way
   to hide a post fast, and a record of what was done.
7. **A platform changes or blocks us:** YouTube / SoundCloud / Bandcamp /
   Mixcloud embeds and page formats change without warning — each reader
   and player should fail gracefully (a "can't play here → open it ↗"
   link, the queue skipping) rather than break the card; the admin log
   should flag a reader that suddenly fails a lot.
8. **Costs running away:** email, server and any paid API with spending
   caps / alerts.
9. **Bad actors in shared spaces:** playlist invite links and walls are
   open by link — let owners revoke links (exists), remove friends
   (exists) and report.

**E. Search split + fewer ads (gabriel, 4 Oct)**
1. **Split track searches across platforms** once the APIs are in
   (section 1): spread lookups over YouTube, Spotify, Deezer, SoundCloud
   etc. so no single quota runs out, and fill a track's embed links from
   another platform when one is down or out of quota. gabriel applies for
   the YouTube quota increase later (free, but a compliance review — needs
   the live site, privacy policy mentioning YouTube + Google's policy, and
   terms first; takes weeks).
2. **Ads in embedded players** can't be removed (the platform's choice;
   stripping / proxying / re-hosting audio breaks their terms and
   copyright — never do it). What we can do:
   - store **several links per track** (YouTube, Bandcamp, SoundCloud,
     Mixcloud…) and have the queue **prefer ad-free sources** — Bandcamp
     (no ads), SoundCloud / Mixcloud embeds (no audio ads at present —
     re-check) — with YouTube as the fallback (monetised videos show ads,
     most label releases are);
   - a per-track "play from" switch and a "prefer Bandcamp / SoundCloud"
     setting;
   - a note that YouTube Premium listeners signed in to YouTube get no ads
     in embeds;
   - later, opt-in: Spotify (Web Playback SDK) / Apple Music (MusicKit)
     full ad-free playback for subscribers who connect their account.
   Ads play before a video starts, so they don't break the queue — they
   just add a pause.

**F. Done / decided on 4 Oct (a questions-only morning)**
- **About → "Listening without interruptions"** (`Drawers.jsx` AboutDrawer):
  sign in to your platforms in this browser; YouTube Premium removes its
  ads in the embeds too when signed in; Bandcamp has no ads (BUY ↗).
  **No ad-blocker suggestions, however worded** — the YouTube embed terms
  forbid encouraging blocking ads; it would risk the API key and embeds.
  gabriel agreed.
- **Next session = a big one, moving towards launch, no rush.** The
  initial public feedback was good — take it on board and **polish the
  product first.** gabriel brings the feedback notes; start by turning
  them into a plan, then: the feed-dropdown tidy-up ("later" item 5),
  then section 9 A (phone layout, email, security pass, legal pages,
  backups), then hosting + the real name, then the YouTube quota
  application once the site and legal pages are live.

**D. Worth having by launch, not blockers**
- Privacy-friendly analytics (Plausible / self-hosted) to see what people
  actually use — mention it in the privacy policy.
- Accessibility pass (keyboard, contrast, screen readers) on the cards,
  drawers and player.
- A status line in the admin drawer for API quotas, email sends and crawl
  health (partly exists).
- SEO and the page-per-post (section 5) so the surge leaves search traffic
  behind.

### 12. ★★ YouTube API quota increase — premium priority (gabriel, 4 Oct)

Why it's top: track search (~50 searches a day today), the split search,
"send to YouTube" (~1,000 units per 20-track playlist) and a launch spike
all run out of the default 10,000 units / day. The increase is **free** but
a **compliance review** by Google that takes weeks (sometimes rounds of
questions) and can be refused — so get the site compliant early and apply
as soon as it can pass.

**Timing (agreed 4 Oct): prepare before launch, apply just after.**
- **Before launch:** the compliance audit (data retention) and the
  privacy policy + terms — needed for launch anyway.
- **Soft launch** (invite-only / waitlist, section 9 B7) to keep demand
  inside 10,000 units / day while gathering **a few weeks of real usage**
  (admin Status logs daily quota) → then apply with real numbers, not
  projections. First ask roughly **150,000–250,000 units / day** (estimate
  for ~1,000 daily users: ~50k searches + ~50k exports + crawl, ×2
  headroom) — refine from the data. Google grants what's justified, often
  part at first; re-applying later is normal.
- Bridge until it's granted: stored links / crawled uploads before
  searching, split searches across Spotify / Deezer, search only on click,
  the existing "searching paused for today" state, and **hold "send to
  YouTube" until after the increase** (the biggest user).

Steps:

- [ ] **Audit our YouTube use against the YouTube API Services Terms and
      Developer Policies** — especially how long we keep API data:
      `youtube_cache`, `release_track_links` (YouTube links per track,
      kept indefinitely), `yt_channels` / `yt_channel_videos` (crawled
      uploads), `youtube_channel_cache`. The policies limit storing API data
      and require refreshing or deleting it; fix whatever doesn't comply
      (e.g. refresh / expire on a schedule) before applying.
- [ ] Embedded player rules: visible player, not covered, no audio-only /
      background play, no stripping of ads or branding (our cards, the
      queue player and the planned phone app all respect this — keep it so).
- [ ] **Privacy policy** naming YouTube API Services, linking Google's
      privacy policy, saying what YouTube data we store and how users can
      revoke access; **terms of use** referring to YouTube's terms.
- [ ] **Live site on the real domain** (section 9 A1) — reviewers look at
      it; a test account for them if anything sits behind sign-in.
- [ ] Measure current usage (the admin Status already shows daily quota)
      and **work out the units needed** with headroom: searches per day,
      channel crawl, playlist exports.
- [ ] Fill in Google's "YouTube API Services – Audit and Quota Extension"
      form: what the site is, every API call and why, screenshots / a
      screen-recording of each feature using the API, the number asked for.
- [ ] Later, for "send to YouTube": Google OAuth app verification for
      the YouTube scope (privacy policy, demo video, domain) — can be done
      alongside or after.
- [ ] Keep records (what was sent, replies) — the next increase or a

### 11. ★ Player on the go — top priority from public feedback (4 Oct)

People want a **continuous cross-platform player they can use on the go**
(their playlists, phone in pocket, screen off). The honest constraint: no
outside site can mix YouTube / SoundCloud / Bandcamp embeds into one
stream that keeps playing in the background — YouTube forbids background
play of its embeds (only its own apps, with Premium) and iOS stops web
audio in the background. **Never** work around it by extracting / proxying
audio or keeping hidden players alive — it breaks the terms and would cost
the API key and the embeds. The ways that work:

1. **"Play on my service"** (the main answer): the listener picks Spotify /
   Apple Music / YouTube Music / Tidal / Deezer once; each playlist track is
   matched to that service (ISRC / UPC via the platform APIs in section 1,
   plus a link resolver such as Odesli / song.link — check its terms) and
   played by that service's SDK or app → background + lock screen, legit.
   Spotify iOS / Android SDK (App Remote: our app is the remote, the Spotify
   app plays), Spotify Web Playback SDK (Premium), Apple MusicKit
   (subscribers). **Read each SDK's current terms** — Spotify has rules on
   mixing its content with other sources in one player, Premium needs, etc.
2. **Unmatched tracks** (common for underground / Bandcamp-only releases):
   fall back to sources that can play plain audio in the background
   (Bandcamp, maybe Mixcloud — test in a native wrapper with background
   audio enabled), else skip with a note / "save for home".
2b. **"Pocket mode"** (gabriel's idea, 4 Oct): built into the queue — when
   the screen locks / app goes to the background, swap the current and
   upcoming tracks to their **Bandcamp / SoundCloud versions** where we've
   found one (the multi-link-per-track work, section 9 E), and go back to
   the normal sources when the app opens again. Those players don't carry
   YouTube's background ban — still read their current terms. Notes:
   - **iPhones block starting new sound in the background**, esp. on the
     phone website. Most reliable: a **"pocket mode" button tapped before
     locking** (the tap is the permission) that pre-switches the queue
     while the screen is on. Automatic switch on lock: better in the store
     app (background audio enabled) than the website — test on real phones.
   - Tracks with no Bandcamp / SoundCloud version are **skipped and saved
     for later** ("3 tracks were skipped while your screen was off — play
     them now?").
   - Versions can differ (master, edit, length); SoundCloud can seek to
     about the same point, Bandcamp starts from the top.
   - Switch back at the **next track**, not mid-song, when the app reopens.
   - First-use prompt, honest: "Pocket mode: while your screen is off we
     play the Bandcamp or SoundCloud version of each track where we can find
     one — it may sound slightly different, and tracks without one are
     skipped for later."
   - Still never extract raw audio from any player — use their real players.
   - **Leaning (gabriel, 4 Oct): the phone app is ALWAYS in pocket mode —
     audio-first by default.** It plays the Bandcamp / SoundCloud (Mixcloud
     for sets) version wherever one exists; YouTube is a screen-on "watch
     this one" option. No switching at lock time, one kind of player, suits
     the audience. Still open:
     - **next track with the screen off** = loading a player in the
       background, which iPhones resist → **reuse one player** (SoundCloud's
       widget can load the next track into itself; a Bandcamp album player
       runs its own tracks). **Prototype this in a native wrapper on real
       phones first — it decides whether the idea works.**
     - YouTube-only tracks are marked "screen on" — skipped in the
       background, saved for later.
     - coverage decides how good it feels → the match-rate test measures
       Bandcamp / SoundCloud versions too.
     - one-time prompt: "On your phone we play the Bandcamp, SoundCloud or
       Mixcloud version so it keeps going with your screen off. YouTube-only
       tracks play when the app is open."
3. **"Send to my service"** — one tap builds the playlist in the
   listener's own Spotify / YouTube Music / Apple Music account (their
   APIs, OAuth). Plays anywhere; carries the site's name (word of mouth).
3b. **"Send to YouTube"** (gabriel, 4 Oct) — the best on-the-go option for
   YouTube Premium listeners: one tap turns a playlist into a playlist in
   *their* YouTube account (shows in YouTube Music too → background play
   for Premium). Official YouTube Data API: Google sign-in (OAuth, manage
   their YouTube playlists), `playlists.insert` + `playlistItems.insert`.
   - Quota: ~50 units per playlist + ~50 per track → a 20-track playlist
     ≈ 1,000 units (~9 exports a day on the default 10,000) — needs the
     quota increase first.
   - Tracks without a YouTube link: match from what we store (saved links,
     crawled channel uploads), a link resolver where its terms allow; search
     costs 100 units each, so use sparingly; skip and say so ("17 of 20
     sent — 3 aren't on YouTube").
   - Google verifies apps asking to manage YouTube accounts (privacy
     policy, demo video, real domain) — another review alongside the quota
     one. Re-sending updates the same playlist, no duplicates.
   - **A YouTube partnership later** — from traction, not a form. Pitch:
     the site sends listeners *into* YouTube / YouTube Music (views,
     playlists, a reason for Premium). Groundwork: follow the API terms to
     the letter, pass the quota + app reviews, measure exports / plays sent
     their way, grow users. Google for Startups is a realistic first door
     (credits, contacts — not special YouTube rights). Don't plan the
     product around it.
4. **"Continue in YouTube"** — open the current track in the YouTube app
   (background for Premium users there).
5. At home / app open: the existing cross-platform queue (QueueBar) as now.

Longer term:
- **Direct uploads by artists / labels** who own their rights — playable
  anywhere incl. background; turns the site into a platform (copyright
  checks, moderation, storage / streaming costs). Fits the underground /
  Bandcamp audience well.
- Licensing music ourselves (a streaming service) is very expensive — not
  realistic early; a licensed internet-radio mode (PRS / PPL) is more
  affordable and could be explored.

**Action list (in order):**
- [ ] gabriel shares a handful of real tester playlists (or just artist +
      track names).
- [ ] **Match-rate test** on them: how many tracks match on Spotify and
      Apple Music, and how many have a Bandcamp / SoundCloud (Mixcloud for
      sets) version alongside YouTube.
- [ ] Read the current terms: Spotify SDKs (mixing sources, Premium),
      Apple MusicKit, SoundCloud widget, Bandcamp embeds, Mixcloud widget,
      Odesli / song.link — for background play and matching.
- [ ] **Background test** in a native wrapper (Capacitor) on a real iPhone
      and Android phone: does the next track start with the screen off when
      one SoundCloud widget / Bandcamp album player is reused?
- [ ] Decide with gabriel from those numbers: always-pocket-mode phone app,
      "play on my service", or both (likely both) — then design (mockup).

**First step: a small test.** Take a few real playlists from testers and

### 10. Phone app (gabriel, 4 Oct: "will inevitably have to be developed")

**gabriel's vision — the app is its own design, not a shrunk web app:**
it works like Tinder's swipe, but **not yes / no** — a swipe just moves
through the feed, **one post per screen**, to the next (or back). The
assets are already in place: the same feeds (my feed, main, walls,
playlist feeds), posts, players, ♡ / + list, following — only the
presentation changes. Design it first (a clickable phone mockup):
- one full-screen card per post — cover / player, artist, title, label,
  feed number + "main #N", the post's text;
- swipe left / right (or up) to move on, back to return; tap to play,
  so the swipe can feel like flicking through records in a crate;
- ♡ a track, + list, follow, open wall within thumb reach;
- what happens to music when you swipe — keep playing the current track,
  or start the next card's (maybe a setting); ties into the queue;
- spotlights as their own swipeable cards; drawers become sheets.
This also suggests the **phone website (step 1) could use the same
swipe-a-card layout** rather than squeezing the horizontal desktop feed —
decide that when designing the mobile layout (section 9 A6).

Suggested route, cheapest first — each step is useful on its own:
1. **Phone-friendly website first** (section 9 A6 — the layout is broken
   at 375px today). Everything else builds on it, and a launch spike lands
   on phones.
2. **Installable web app (PWA):** manifest + icons + a service worker for
   the app shell, so people can "Add to home screen" and it opens full
   screen like an app. Media Session API for lock-screen titles / controls
   where the browser allows. No app stores, same code.
3. **Store apps by wrapping the site** (Capacitor or similar) once the PWA
   works — one codebase for iOS + Android, adds push notifications, deep
   links (`/?wall=`, `/?playlist=` …) and store presence.
4. **Fully native (React Native etc.)** only if the wrapper hits limits.

Things to know before committing to store apps:
- **Background / lock-screen playback is the hard part.** YouTube's terms
  don't allow playing its embeds in the background or with the screen
  off, and iOS stops web audio in the background anyway. Bandcamp /
  SoundCloud / Mixcloud players behave better; Spotify / Apple Music need
  their own SDKs (subscribers). The cross-platform queue will feel more
  limited in an app than on desktop — design for that honestly.
- **Ads:** in an app's webview the user isn't signed in to YouTube etc. as
  they are in their browser, so the "sign in to your platforms / Premium"
  tip works less well there.
- **App store review** checks for embedded-content rights, a privacy
  policy, account deletion inside the app (Apple requires it), and user
  reporting / blocking for user-generated content — all already on the
  launch list (section 9), so do those first.
- Sessions: today's token in localStorage works in a wrapper, but the
  security pass (httpOnly cookie) needs a plan for the app too.

### Known limits

- Discogs **masters** show a "—" type tag for a few seconds on first view.
- The backup fill attaches a Discogs artist id when only one artist has the
